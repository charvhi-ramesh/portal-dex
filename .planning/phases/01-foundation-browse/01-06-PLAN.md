## Phase Goal

ROADMAP Phase 1 goal (verbatim, not in user-story form): Users can browse, search and filter every character as cards in an accessible dark cosmic layout, with state that survives refresh and back navigation.

> MVP note: no user story was invented; run `/gsd-mvp-phase 1` if the canonical form is wanted.

<objective>
Encode the Browse data policies as pure, unit-tested functions: exact-species load steps with the 404 rules, the derived Human total, de-duplication, and every count and announcement string; and pin the DATA-05 QueryClient defaults with tests.

Purpose: BRW-04 is a correctness problem (the API's `species=` is a substring match), and RESEARCH's key insight is that every hard part of this phase is policy. Plans 01-08 and 01-10 wire these functions into the UI; this plan proves them first against recorded fixtures and one live read.
Output: `lib/browse/species.ts`, `lib/browse/steps.ts`, `lib/browse/announce.ts` with tests, and `lib/query/client.test.ts`.
</objective>

## Flagged Assumptions

- **[edge BRW-04 / unclassified, unresolved]** Assumed edges, not probe-verified: only Human overlaps another chip's species (verified on the 826-record dataset, RESEARCH A10), so `deriveTotal` subtracts only for Human; exact matching is case-sensitive on canonical API values; if the humanoid count request fails, the total stays null and the count line keeps "Counting..." (the UI never shows a guessed number).
- **[RESEARCH A4, interpretation of SPEC 5.3]** One infinite-query page is a "load step" that fills to at least 20 exact items with a 4-API-page cap, instead of auto-requesting the next page whenever a page yields fewer than 20 (which would chain through all 22 Human pages). The behaviour difference is visible only for Human. Rated reversible (contained in steps.ts behind browseOptions); confirm at UAT if strict per-page loading is preferred.
