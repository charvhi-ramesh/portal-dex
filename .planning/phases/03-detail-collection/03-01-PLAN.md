## Decisions taken in this plan (Claude's discretion, all reversible)

- **Route shape (Next 16 Cache Components):** `generateStaticParams` returns one sample (`[{ id: "1" }]`) so the page may read `params` at the top level (local docs `dynamic-routes.md` "With Cache Components"); other IDs render on first request. Because no Suspense boundary sits above the page, `notFound()` runs before streaming starts and the response is a real HTTP 404. Fallback if `npm run build` rejects this shape: wrap the param read in `<Suspense>` per the same doc's "Without generateStaticParams" example (the inner component keeps the same narrowing: `routeCharacterId(id)`, `notFound()` on null, and only the validated number passed to `CharacterDetail`) and change the smoke tokens for invalid IDs from `route404:` to `route:` (the not-found copy still renders, with status 200 and a noindex tag).
- **Client 404 for well-formed unknown IDs (99999):** the API answer arrives in the browser, so `CharacterDetail` renders `NotFoundContent` itself. The local `not-found.md` documents `notFound()` for Server Components, Server Functions and Route Handlers only, so the client path does not call it.
- **Title:** the server cannot know the name without a server-side API read (prohibited), so `generateMetadata` gives "Character" (or the 404 title for an invalid ID) and `CharacterDetail` sets `document.title` to `detailTitle(name)` in an effect once the character is known.
- **Hero facts** reuse `backFacts` (so the hero also shows "Appears in N episodes"); origin and location are never links because no location page exists in scope.

## Flagged Assumptions

- **Client 404 status:** `/character/99999` is served with status 200 (the shell) and shows the 404 content after the API answers 404 in the browser. A server-side status would need a server-side API read, which the prohibition forbids.
- **Detail title source:** the tab reads "Character · Portal Dex" until the character is known, then `detailTitle(name)`; on Activity re-show the effect re-applies the name.
- **Canon referral (not minted):** XSS through API strings is canon, covered by `/gsd-secure-phase` and T-03-02.
- **Known limitation, hero image failure (checker I-5, no scope added):** the hero's "initial tile if the image fails" relies on `CardAvatar`'s failure path. Its pre-hydration check (the image ref callback) only recognises a finished, successful load (`complete` with `naturalWidth > 0`); an image that already failed before hydration never fires `onError` and leaves `CardAvatar` in its loading state (an empty surface-raised box, no initial tile). The hero is rendered only on the client after the character query resolves, so its image normally starts loading after React has attached `onError` and the tile appears; the case is checked by the hero image-failure step in Task 2's human-check (UAT item 2) and, if it shows an empty box, is recorded and reported rather than fixed here.
