## User-accepted decisions (2026-11-12)

- **What morphs: the whole card, not only the avatar (user decision, 2026-11-12).** The whole card (its `article`) morphs into the hero avatar box. "View details" sits on the card's back face, and while the back shows, the avatar is on the front face rotated by 180 degrees with its backface hidden, so naming the avatar itself would capture a mirrored or invisible snapshot. This knowingly deviates from the literal wording "the avatar morphs" in DET-02 ("Avatar morphs from the card into the hero") and SPEC 5.4 ("the avatar morphs from the card into the hero"); the user reviewed checker warning W3 and chose to keep the whole-card morph. The fallback is unchanged: one edit in components/card/character-card.tsx removes the card's `ViewTransition` wrapper, and every arrival then fades in. How the whole-card snapshot looks while it scales into the square hero avatar box is judged in UAT (Task 3 human-check, UAT item 4).
- **Browser-generated size interpolation (accepted exception, 2026-11-12, checker I-3).** The `::view-transition-group(.card-morph)` animation that moves the card snapshot onto the hero box is generated by the browser and interpolates `width` and `height` as well as `transform`. That is an accepted exception to the project constraint "only animate transform and opacity", accepted together with the View Transitions morph SPEC 5.4 mandates; this plan's own keyframes and CSS still animate opacity only, and the reduced-motion override turns the group animation off. The executor records this exception in the SUMMARY (Task 3 action step 6).

## Decisions taken in this plan (Claude's discretion, all reversible)

- **What morphs:** see "User-accepted decisions (2026-11-12)" above (the whole card, user decision).
- **When it morphs:** only navigations tagged with the `card-detail` transition type (View details on a card or under the Home card). Header links between Browse and Collection share characters but must not send cards flying, and browser Back carries no type, so neither morphs.
- **Same commit:** View details seeds `characterOptions(id)` with the character already on screen, so the destination hero renders in the navigation commit (the local view-transitions guide: the morph only plays when the destination renders in the same commit).
- **30-minute fallback (SPEC 5.4):** no browser is available to the executor, so "clean" is judged in UAT. If UAT finds it not clean, the fallback is one edit in components/card/character-card.tsx: remove the card's `ViewTransition` wrapper. The hero keeps `enter="detail-fade"`, so every arrival then fades in. If `npm run build` or lint rejects the `ViewTransition` usage, apply that fallback at once and record it in the SUMMARY.
- **Mini cards** do not carry a transition name, so a detail-to-detail hop fades rather than flying the previous hero around.
